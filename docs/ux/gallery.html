Code-Shipper — operator surface wireframes

Proposals for the three operator surfaces: scriptable CLI, interactive TUI (/ship-ui), and the Hermes Desktop plugin page. One shared lifecycle, one shared state vocabulary, one rule: humans merge — no surface presents “merge” as an agent action.

Proposal for approval — not implemented
Lifecycle 1 · CLI 2 · TUI 3 · Desktop 3b · Policy editor 3c · Audit trail

0Shared lifecycle and state vocabulary

Every surface renders the same projection. The seven states below are the whole story; colour is always paired with text. Review verdict, CI, policy and approval are four independent signals — no single green badge compresses them into “safe”.

PR found→ review running→ verdict: approve / approve-with-issues / needs-fix→ fix loop (optional): patch → push → CI rerun→ approval requested→ approval granted→ ready for human merge — on GitHub, by you

The fix loop returns to review running after every push (a fix can start another review). “Ready for human merge” is a terminal state for Code-Shipper: the only action offered is Open PR on GitHub. Approval is granted either by a person, or by the agent only where the repo policy allows it and the off-by-default authority flag (D1) is on.

1CLI — concise receipts, deeper on demand

Plain output leads with the result or the blocker, then PR/head, next action, run ownership and the stop command. Every command also takes --json (one envelope on stdout, progress on stderr, unknown cost is null — never $0). There is no ship merge.

CommandWhat it doesEnds with
ship statusInbox of watched PRs, sorted needs-you-first, with the reason in words.Next action per PR.
ship review <pr>Reviews the PR at its current head: find → verify → rank → post. Never approves or blocks.Verdict + receipt.
ship watch <pr>Starts (or --stops) the fix loop: failing checks, conflicts, review comments, Important findings.Budgets + stop command.
ship approve <pr>Evaluates the repo approval policy at the exact head; records the agent approval only where every condition holds. Refuses with a reason code otherwise.Granted / refused + who is still needed.
ship policy <pr>Explains the effective policy: which rule governs each changed file, strictest wins, who must approve.Counted approvals at head.

2TUI — keyboard review workbench (/ship-ui)

A modal widget that owns the keys while open, distinct from the /ship action command. Arrow keys / jk move, Enter opens, single-key confirms for the common actions — with Back as the default on every consequential prompt. Escape only ever closes the view; s (stop watching) and x (cancel run) are separate, labelled actions. There is no merge key.

3Desktop — Hermes plugin page: attention inbox + review workspace

A full /code-shipper page in Hermes Desktop (route + sidebar nav), inheriting the host theme. Three regions at wide width: an attention-first inbox, the selected PR’s working tabs, and a context rail with run ownership, budgets and the authority boundary. No merge button anywhere — the terminal state links out to GitHub.

Policy editor — effective vs proposed, never self-applied

The effective policy is read from the default branch only and is read-only here. Edits are a proposed overlay: validated live, applied to nothing, and clearly labelled “not effective until merged”. A PR that changes the policy is never judged by its own new rules.

Audit trail — every write, refusal and uncertain outcome

Append-only receipts with the exact head each action was computed for. Refusals are first-class rows — an agent that was stopped is as auditable as one that acted. Uncertain writes stay open until read-back settles them; nothing is silently retried.
